# 目标编写

把用户请求写成一个持久目标，让后续轮次无需猜测对话意图就能继续执行。

## 工作流

1. 确认用户明确要求 Goal 模式或跨多轮的持久目标。不能仅因任务复杂就推断用户要使用 Goal 模式。
2. 保留请求中明确提及的所有交付物、文件、命令、Skill、审批要求、发布步骤和成功标准。
3. 编写一个简洁目标，包含：
   - 要实现的具体结果；
   - 能证明完成的权威证据；
   - 约束和必须遵循的工作流；
   - 授权与范围边界；
   - 遇到失败或审查意见后的迭代方式；
   - 确实需要停下来等待用户输入的条件。
4. 检查目标在上下文压缩后仍可执行，不能靠一段看似可信却未经验证的最终回复宣称完成。
5. 调用 `create_goal` 并传入目标。创建 Goal 会替换该任务原有的 Goal，因此只能为当前正在处理的明确请求执行此操作。

## 编写规则

- 写清结果和证据，不写猜测性的实施计划。
- 用户原话明确指定产物或工作流时，保留其措辞。
- 使用与任务相称的验证，不添加无关检查门槛。
- 把审批、凭据、破坏性操作和外部协调视为边界，不能据此绕过权限。
- 阻塞指确实需要用户输入或外部状态变化才能继续的困境，不是任务困难或首次尝试失败。
- 不添加 Token 预算。
- 不把 Goal 标记为完成；后续执行轮次必须严格核对证据后才能完成目标。

## 目标结构

下面的结构用于检查内容是否完整，不是必须照抄的模板：

```text
实现<具体结果>。保留<约束与边界>。使用<必要工作流或 Skill>。
通过<权威证据>验证完成。如果验证或审查发现需要处理的问题，修复后重跑相关检查。
只有在<真正的阻塞条件>下才停下来等待用户。
```
