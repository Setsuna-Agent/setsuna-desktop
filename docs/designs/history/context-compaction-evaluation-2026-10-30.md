# 上下文压缩实现与评测记录（2026-10-30）

三个阶段均已落地：共享模型请求与原生压缩、完整输入的可移植交接和条件安装、后台预计算及真实供应商续跑评测。当前协议和生命周期规则以[执行方案](../current/context-compaction.md)为准。本记录保留当时的结果与启用决策，不作为模型质量保证。

## 实现验收

- 普通采样与 V2 使用同一个 Pi 请求转换，覆盖真实指令、工具、图片和 provider replay；仅明确不支持时降级到独立端点或可移植交接。
- 可移植摘要按输入预算完整分批，恢复工作集工具正文，保留用户原文与修正；检查压缩后完整请求的目标和续跑余量。
- SQLite 写入队列内验证来源、窗口版本和预算，再提交检查点；追加后缀保留，删除、改写、切换模型与重启不会重放不兼容来源。
- 后台与前台共用候选生成和安装；每线程单任务、全局最多两个生成，软阈值不等待，硬阈值接管同一候选。失败、配置变化、取消、删除、迁移和关闭均有清理路径。
- 用量在模型调用结束时记录，不依赖候选是否安装；Goal 在推进结算水位前等待本轮后台用量，最终回答已经先发布。
- 定向验证覆盖后台生命周期 11 项、AgentLoop 集成 5 项，以及原生协议、长消息分批、SQLite 条件提交和恢复。完整检查结果在本文末尾。

## 真实评测方法

入口为 `pnpm benchmark:context-compaction`，实现位于 `packages/desktop-runtime/test/evaluation/`，使用实际 Pi 客户端、runtime compactor、SQLite 和配置中的供应商凭据。只有合成内容发送给模型；不读取用户对话，不修改供应商设置。复跑参数见[测试文档](../../development/testing.md#上下文压缩真实供应商评测)。

每条策略连续安装五个检查点。五份中文工具结果把唯一证据埋在长文本中部；交付必须包含累计代码、三次用户修正后的负责人和 limit、原有平台顺序、图片中的字符。模型可以回查工具；调用与结果真实写入临时 SQLite，进入下一轮。第三轮后关闭数据库并恢复，第四轮切换供应商/模型并把本地窗口从至少 48k 收紧到至少 24k。新实现另执行真实请求取消，验证取消不改写历史。

两组任务使用相同合成任务和评分器：

- **可移植组**：配置中的 `gpt-6-luna` 做摘要及前三轮续跑，后两轮续跑切到 `gpt-6-sol`，摘要仍由显式 task model 执行。
- **原生组**：配置中的 Responses `gpt-6-sol` 前三轮实际返回 `responses-v2`，后两轮切到另一供应商的 `gpt-6-luna`，恢复来源并改用可移植交接。因此这是三次原生加两次跨模型交接，不是五次同模型原生压缩。

这些是用户配置的兼容网关和模型标识，不能据此认定直连 OpenAI，或认定网关内部模型实现等同 Codex。独立 `/responses/compact` 的完整窗口和降级路径由 HTTP/SSE 协议测试覆盖，本轮未取得该端点的真实续跑数据。

旧基线取自仓库 `e169245d2a2cfcc95166bb7ba6af4e03bc4065ff` 的 runtime compactor，仍共用当前 Pi 传输层。因此比较的是窗口选择、交接和安装行为，不是旧版完整应用对新版完整应用的发布基准。

完成的每组新实现均安装五个检查点，第三轮恢复和末尾取消校验通过。旧原生组最后一轮漏掉第四份证据；旧实现两组的第一个检查点都没有释放足够请求空间，估算余量分别为 -1,051 和 -1,093 tokens。完成的新版运行余量始终为正。窗口显著缩小，但回查和生成开销使本次用量没有全面下降，不能宣传为省 token 或稳定提速。

后台对照人为重叠一秒工作，每轮 `compactionMs - foregroundBlockedMs` 约为一秒。每策略仅五个样本，最近秩 p95 就是最大值；不同时间的供应商延迟、缓存命中和并行评测会影响结果，不能将表中的差异直接归因为调度算法。

压缩间隔是受控变量：每次追加一批新证据及上一轮真实回查记录，再触发压缩。数据记录 `appendedMessagesSinceCompaction`（完成运行中为 6–12 条）、`estimatedHeadroomTokens` 与每轮输入/输出窗口。它验证五次连续压缩和余量，不能估计生产中的自然压缩频率；未进行长时间随机负载或不同操作系统的性能统计。

## 失败、修正和复测

1. 早期可移植交接把图片字符 `VISION-Z9` 误读成 `VISION-9` 并延续，另有返回数组而非单个字符串的输出；摘要还自行推断每批都需要独立视觉码。交接规则已补充原样保留标识符、数据类型、视觉不确定性和不扩大任务范围。后续运行通过这些字段，但一次通过不能证明模型不再误读。早期数据明确标记为预备运行，当时回查记录未持久化，不混入最终性能表。
2. 最终可移植前台首次在第三轮触达四次续跑请求上限，前两轮通过。五份文件可能被顺序回查，评测上限调整为八次，允许回查后交付，并保留失败窗口与工具调用信息；独立复测五轮通过。模型输出仍有随机性，不能把复测成功全部归因于上限调整。
3. 原生后台首次已取得 V2 检查点，但随后的续跑请求在 120 秒时超时，未交付第一轮。独立复测五轮通过。该超时的具体供应商侧根因没有证实；没有把它缓存为“不支持”，也没有放宽生产协议校验或隐藏失败。
4. 预备评测发现背景策略有轮次未真正安装检查点，原因是脚本阈值没有保证到达硬边界。已修正阈值并逐轮断言安装数量；相关预备延迟数据不用于本表。工具回查落盘、完整恢复比较也已补齐。

## 启用决策

`features.backgroundContextCompaction` 保持默认关闭，可通过“设置 → 实验性功能 → 后台上下文压缩”开关启用；前台协议、预算、窗口提交和恢复改进正常生效。后台关闭是本轮完整评测后的启用决策，不是未实现的阶段占位。

理由是单一合成任务的小样本不能证明广泛任务保持能力；真实运行仍出现超时、额外回查和视觉不稳定，且新实现总用量未全面降低。这里没有声称复制 Codex 服务端的 opaque 模型压缩，也没有将协议测试当作真实编码任务完成率。扩大自动启用范围需要更多任务和供应商数据，属于后续发布决策，不再留未接入的实现路径。
