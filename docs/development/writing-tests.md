# 测试编写规范

Coding agent 在新增、修改或重写测试前必须完整阅读本文。测试的取舍、断言和时序规则以本文为准；环境、脚本、测试分层和验证范围见 [测试与验证](testing.md)。

本仓库只保留有显著收益的测试。测试数量、覆盖率和“防止回退”都不能单独成为新增测试的理由。低风险的直接赋值、薄转发、展示格式或样式变更，默认不补测试。

## 一、先证明值得测

写测试前，先读真实调用链和已有覆盖，回答三个问题：

1. 它能发现什么具体且有实际影响的错误？例如丢失用户数据、重复执行操作、越权访问、跨会话污染、保存失败后丢失草稿、关闭后继续写入。
2. 测试是否执行了决定这个结果的生产逻辑，并检查了调用方、持久数据或外部能力能观察到的结果？
3. 相比已有测试，它增加了什么独立验证？收益是否值得额外的 fixture、mock、运行时间和维护成本？

说不清这些问题，就不要写。不能只把“新增了一个函数”“修了一个 bug”“以前有这个测试”当作依据。一个场景已经能通过合适的业务入口验证时，不再为它经过的每个组件、hook 和转发方法各写一份。

优先覆盖存在实际风险的分支，不要求每项改动都机械补齐成功、失败、取消、恢复的全套用例。

| 值得验证的结果 | 不值得单独保留的断言 |
| --- | --- |
| 保存失败保留草稿，重试后持久化正确数据 | 保存按钮的固定文案、错误文字的位置 |
| 被拒绝或重复提交的审批不会执行本机操作 | 页面上出现“允许”“拒绝” |
| A 会话的迟到结果不能覆盖已切换到的 B 会话 | 选中行的类名、图标或 DOM 顺序 |
| 重启恢复完整事件，过期 owner 不能继续写入 | 构造参数原样回显、对象字段数量 |
| 真实路径逃逸被拒绝，导出结果不泄露凭据 | 源码里包含安全检查函数名或提示词句子 |
| 核心就绪不等待被阻塞的外围任务，退出后不再注册 | 本机一次执行耗时小于任意毫秒阈值 |

## 二、直接删除低价值用例

以下用例不新增；遇到已有用例时，确认真实职责和其他覆盖后直接删除：

- 只锁定 UI 展示：CSS、类名、颜色、字体、图标、DOM 排列、布局尺寸、动画、固定标题或辅助文案。
- 只复制静态定义：常量清单、默认配置、注册项顺序、依赖声明、源码或 CSS 字符串；没有执行真正消费它们的行为。
- 把 fixture 的名称、文本或字段传进去，再断言原样出现；没有验证实际处理规则。
- 替换掉待测规则，再断言 mock 返回了预设值；或者只验证一个没有业务判断的转发方法调用了 mock。
- 将同一组输入、逻辑和预期复制到多个层，或者在测试里重写生产算法来计算预期。
- 为一个低影响的展示差异引入大量宿主、插件、计时器或进程 fixture。

混合用例只删除无价值的场景和断言，保留其中有实际收益的行为验证。随之清理不再使用的 helper、fixture、import 和文档引用。不要删掉旧展示断言后，再换个选择器、措辞或文件位置补回同类测试。

按实际验证目的判断，不按断言语法一刀切：输出中的凭据泄露、协议编码、命令转义、UTF-8 边界和解析结果都可能值得做字符串断言；审批拒绝后的零次执行、防重复提交的一次执行，也值得检查 mock 调用。关键是这些断言是否验证了真实规则和后果。

## 三、选择能暴露错误的最小范围

- 纯数据规则直接测生产 reducer、parser 或 helper，预期由业务规则给出。
- 保存、切换、取消、重试等行为，测拥有该状态的真实 service、coordinator 或 hook；必要时通过真实交互触发。
- 文件、SQLite、HTTP、IPC 或原生进程的错误只有经过对应边界才能暴露时，才使用真实边界做集成测试。
- 同一行为在多个层都有测试时，应能说明各自保护的不同约束，例如路径解析与真实符号链接逃逸；不能只是换一套 mock 再重复一次。

Mock 和 fake 放在外部能力边界，例如模型响应、远端请求、原生操作、时钟或用户决定。待测规则、状态流转和持久化结果保持真实。不要为了省 fixture 把核心逻辑也 mock 掉，也不要为证明一个转发参数启动整套 runtime。

Renderer 测试关注实际功能交互：提交的内容、操作目标、重复执行、失败后草稿保留、会话隔离等。查询控件时使用现有 role、label 或稳定的业务标识；不要为了测试给产品追加文案或改变结构。

不为观测内部步骤扩展生产 API，不新建只有测试需要的通用框架、兼容层或复杂配置。Fixture 只准备决定当前结果的数据和能力，优先复用同模块已有的支持代码。

## 四、用明确时序验证异步行为

### 等待下一步真正依赖的条件

禁止通过固定 sleep、空转若干次事件循环、连续几次 `Promise.resolve()` 或不断重跑，猜测异步操作已经走完。

例如，不能用下面的写法证明读取完成：

```ts
await sleep(100);
expect(service.snapshot().loading).toBe(false);
```

等待可观察的完成条件，并验证业务结果：

```ts
await vi.waitFor(() => expect(service.snapshot()).toMatchObject({
  loading: false,
  state: expectedSnapshot,
}));
```

优先使用任务返回的完成 Promise 或对应事件；没有直接完成信号时，再有界等待业务状态。轮询只是等待条件，不能用来重复执行待测操作，或把它的真实错误吞掉再试一次。等待截止时间用于报告挂起，不能作为正确性的证据。

消息完成、`activeTurnId` 清空、任务从 registry 退出、取消清理完成是不同阶段。连续启动轮次或修改历史前，使用所属 harness 表达的完成条件，例如 `waitForCompletedTurn`；涉及删除屏障时，还必须验证旧任务和写入已经排空。

### 先建立竞态，再检查结果

取消、迟到响应、并发保存、删除屏障等测试应明确安排：

1. 用进入信号确认目标请求或处理函数已经开始；用可手动释放的 Promise 保持它未完成。
2. 触发取消、切换会话、第二次保存或删除，验证该阶段的约束，例如新任务被拒绝、旧数据仍未被覆盖。
3. 释放旧操作，等待它真正结束，再检查最终状态、持久数据和外部执行结果。

不要在请求尚未进入时就取消，然后声称覆盖了“执行中取消”。负向断言也需要前置证据：立即检查“尚未调用”不能证明旧结果在完成后仍被隔离。

事件监听必须先于触发操作注册，避免漏掉同步事件。事件流读取应先消费已有缓冲；一次等待超时后复用仍未结束的读取，避免下一次读取丢失消息。

### 只控制需要控制的时间

调度、退避、防抖、租约和超时策略使用注入时钟或 fake timers。明确推进边界前后的时间，验证操作是否执行以及执行后的业务状态。不要把生产逻辑依赖的多个时间来源推进到不同阶段。

真实 HTTP、文件 I/O、端口分配和原生事件仍需等待真实完成。只 fake 所需的计时 API，不要让等待真实 I/O 的保护期限依赖一个不再前进的 fake clock。

普通行为测试不使用墙钟耗时或跨机器性能比例判断正确性。启动链路用被阻塞、失败和取消的外围任务验证核心就绪的独立性；耗时比较与性能测量按照 [启动约束](../architecture/runtime-flows.md#启动性能约束硬性) 和 [基准说明](testing.md#feature-projection-冷重放基准) 执行。

## 五、隔离环境并结束所有资源

- 使用独立临时目录、随机 loopback port、独立 Electron userData 和明确的测试时区或时钟；不读取用户现有数据。
- 不依赖用户 home、全局 Git 配置、系统 rg、当前登录状态或公共模型服务。按需提供明确的 Git identity、工具路径和 fake provider。
- 普通集成测试不从公共包仓库下载依赖。依赖获取固定在外部能力边界或本地 fixture，编译、路径安全和运行链路按验证目标保持真实。不要为规避下载波动而放松生产安全规则。
- 在 `finally`、`afterEach` 或所属 harness 中清理进程、数据库、socket、watcher、订阅、读取流和计时器；释放完成后再删除临时目录，兼顾 Windows 文件句柄约束。
- 恢复全局时钟、环境变量、spy 和 mock；测试失败时也必须执行清理，不能把状态留给下一项测试。
- 生产代码与测试严格分离，测试镜像所属模块放在 `test/`；共享支持代码与 fixture 留在对应模块，遵守架构检查的体积、密度和分层限制。

原生进程测试要同时观察目标行为、完成信号和退出。若用例已经输出成功标记却未退出，应检查资源和关闭流程，不能把“业务成功”当作整个测试完成。

## 六、处理失败和不稳定测试

先确定它是生产错误、环境依赖、未建立的前置条件、等待了错误阶段，还是已经没有价值的断言。记录必要的阶段、事件和退出信息，不靠扩大输出或泄露对话、凭据来排查。

有价值的用例应修正时序或隔离外部依赖；低价值或重复的用例直接删除。不能以恢复 CI 为理由削弱真实安全、数据完整性或恢复约束，也不能通过新增 skip、retry、放宽断言或不断增大 timeout 掩盖失败。合理的退出保护期限应基于被测工作量和失败证据设置。

单次重跑成功只说明没有复现。修复后先运行相关定向检查；对于时序问题，还应在原有并发条件或足以暴露竞态的受控场景中验证，再按 [测试与验证](testing.md) 扩大范围。测试应在真实业务规则被破坏时失败，不应取决于机器快慢或碰巧有利的事件顺序。

## 提交前核对

确认能明确说明：测试保护的具体后果、执行的生产规则、相对已有覆盖的独立收益、异步前置与结束条件，以及失败后的清理。删除仅锁定展示或实现细节的剩余断言；只报告实际运行过的验证及其结果。

可参考现有的 [线程删除屏障](../../packages/desktop-runtime/test/loop/core/agent-loop-deletion.test.ts)、[SQLite 所有权](../../packages/desktop-runtime/test/adapters/store/sqlite-thread-ownership.test.ts)、[HTTP 背压断开](../../apps/desktop/main/test/unit/runtime/native-bridge-system-fetch.test.ts) 和 [watcher 防抖](../../packages/features/review/test/integration/main/review-change-monitor.test.ts)。阅读时关注它们验证的业务约束和控制条件，不复制整套 fixture 或把当前实现的步骤固化成要求。
